# 编程规范执行标准

## 1. 核心原则

### 1.1 优先级

1. 用户在本轮任务中的直接要求
2. 项目需求文档
3. 本文件
4. 已稳定落地且与前 3 项不冲突的现有实现

### 1.2 核心信条

- 代码应写得像稳定的工程契约，而不是临时的个人表达
- 先满足需求和接口，再处理局部风格
- 规则必须可执行、可检查、可复述
- 本文件未写明的规则，不要自行脑补

### 1.3 术语

| 术语 | 含义 |
|------|------|
| **必须** | 无例外执行 |
| **默认** | 通常执行；仅在更高优先级要求冲突时偏离 |
| **建议** | 推荐执行；偏离时应有理由 |
| **禁止** | 一律不允许 |

## 2. 文件与导入

- 文件名必须直接体现职责，禁止 `helpers.py`、`misc.py`、`common.py` 等宽泛命名
- 禁止一个文件承载多个互不相干的职责
- 导入顺序为标准库 → 第三方库 → 项目内部模块，组间不加空行，组内按行长度由短到长排列
- 仅导入实际使用的对象，禁止 `from module import *`
- 允许例外：`try/except ImportError` 中的局部导入、条件分支中的局部导入、`TYPE_CHECKING` 类型导入

## 3. 命名

| 类别 | 风格 |
|------|------|
| 类 | `PascalCase` |
| 常量 | `UPPER_SNAKE_CASE` |
| 变量 / 函数 / 方法 | `snake_case` |
| 私有成员 | `_snake_case` |

- 默认使用完整单词，禁止省略、截断和习惯性缩写
- 布尔命名优先使用 `is_*`、`has_*`、`can_*`、`should_*`
- 缩写仅允许出现在以下窄场景：
  - 参数名后缀，如 `embed_dim`、`num_classes`
  - 业界固定导入别名，如 `np`、`nn`
  - 张量形状解包，如 `B, C, H, W = x.shape`
- 框架强制要求驼峰命名的重写入口允许保留原始命名，如 Qt 的 `paintEvent`；新增的业务方法仍必须使用 `snake_case`
- 跨层边界时，内部值使用 `*_value`，用户可见展示文本使用 `display_*`，禁止用一个字段同时承担两种职责

## 4. 签名与类型提示

- 所有公有函数和方法必须补全参数类型与返回值类型；私有方法默认也应补全，仅极少数动态场景可例外
- 类声明和短签名保持一行；参数过多导致单行超过合理行长时必须换行并按冒号对齐
- 类型写法保持显式，优先使用 `Optional[T]`、`Dict[K, V]`、`Tuple[...]`，同一项目内不要混用过多不同风格的类型写法
- 行长度例外仅限：方法签名、logger 初始化语句、logger 输出语句

## 5. Docstring

### 5.1 基本规则

- 禁止模块级 docstring；公有接口必须具备；私有接口在契约不自明时补充
- 使用三双引号 `"""`，首尾引号各占一行，摘要独占一行且只写一行接口契约，不补充原理解释
- 全局禁止使用括号，仅表述张量形状等技术要求时除外
- 需要字段块时默认顺序为 `Args:`、`Returns:`、`Raises:`、`Attributes:`，参数名与冒号对齐，描述文本保持相同缩进
- 摘要后若还有字段块，必须空一行
- 字段说明默认每项只写一行，不加句号
- docstring 不应写教程式背景、内部步骤拆解、重复函数名已表达的事实

### 5.2 何时补字段块

出现以下任一情况时，不能只写最小形态：
- 参数语义不是签名本身就能看明白
- 返回值含有边界条件、单位、特殊值或哨兵语义
- 可能抛出调用方需要处理的异常
- 类对外暴露了稳定属性契约

以下情形不要求机械补字段块：无参数时不写 `Args:`，返回 `None` 且摘要已足够时不写 `Returns:`，没有稳定向外暴露的异常时不写 `Raises:`

### 5.3 最小合法形态

```python
def close_camera() -> None:
    """
    关闭当前相机连接
    """
```

### 5.4 违例示例

```python
# 三引号与摘要写在同一行
def close_camera() -> None:
    """关闭当前相机连接"""

# 摘要后未空行且未对齐
def create_camera(enable_debug_mode: bool = False) -> UnifiedCameraInterface:
    """
    根据当前运行模式创建相机实现
    Args:
        enable_debug_mode: 是否构建调试相机实现
    """
```

## 6. 注释与括号

### 6.1 注释

- 注释说明逻辑意图，不复述代码字面含义；默认写在代码块上方，禁止行尾注释
- 注释应说明：代码块在完成什么动作、逻辑意图是什么、为什么需要这组操作
- 注释不应说明：某一行代码表面上写了什么、命名已经清楚的赋值语句、语法本身的含义

### 6.2 括号

括号只服务技术语义，不服务自然语言补充：

- 允许：Python 语法必需、数学表达式、区间表达如 `(0, 1000]`、张量形状如 `(N, H, W)`、技术协议接口名如 `calibrate()`、特殊值如 `NaN/inf`
- 禁止：在 docstring / 注释 / 日志 / 异常文本中用括号补充自然语言说明

## 7. 文本语言

### 7.1 语言分类

- 源码层文本（docstring、注释、内部 logger、内部异常文本）默认使用中文
- 用户可见文本（窗口标题、按钮标签、对话框、状态提示等）默认使用英文
- 同一组件链路内不得混用中英文正式文案

### 7.2 中文排版

- 阿拉伯数字两侧不加空格：`支持9x9调色板`，禁止 `支持 9x9 调色板`
- 英文技术词汇两侧不加空格：`返回DebugCamera实例`，禁止 `返回 DebugCamera 实例`

### 7.3 异常文本

- 内部异常使用中文，必须直接、可定位、可调试
- 不把面向用户的安抚性文案写进内部异常
- 进入 UI 前必须在上层转换为正式用户可见文案

### 7.4 Logger

- logger 初始化和输出语句必须各写在一行，优先使用 `%` 格式化，避免 `f-string`
- 内部 logger 默认使用中文，日志应写成完整事件表达
- 操作者可直接看到或会原样进入 UI 的日志，视为用户可见文本，必须使用英文

## 8. 结构与职责

### 8.1 实现层面

- 使用显式状态变量，不把状态隐藏在异常流中
- 使用完整命名表达状态含义
- 并发场景优先保守、清晰、可追踪
- 错误处理优先保证状态可观察与资源可回收
- 接口说明描述调用契约，不描述内部算法

### 8.2 界面链路

| 组件 | 职责 |
|------|------|
| `sections` | 创建控件、布局、样式 |
| `coordinator` | 界面行为、弹窗、标题刷新 |
| `widget` | 渲染与局部绘制 |
| `adapter` / `mapper` / `view model` | 将应用层对象正规化为 GUI 可消费对象 |

执行要求：

- 颜色、字体、窗口尺寸、关键布局比例走集中入口
- 纯局部绘制几何常量可留在 widget 内部
- `sections` 不负责业务判断，`coordinator` 不负责深层业务逻辑，`widget` 不负责发明正式显示词汇
- `status_message` / `error_message` 只能承载应用层产出的正式 UI 文案，GUI 不直接透传底层异常文本

## 9. 审查协议

### 9.1 结论分级

- **硬性违例**：明确违反"必须"或"禁止"
- **需确认**：证据不足，或需要结合上下文判断
- **优化建议**：不构成违例，但存在更稳妥的写法

### 9.2 输出顺序

审查输出必须按以下顺序组织：硬性违例 → 需确认项 → 优化建议

### 9.3 每条结论的最小组成

- **对象**：哪个文件、类、函数或方法
- **问题**：具体哪里不符合规范
- **规则**：对应本文件哪一条
- **方向**：如何修正

### 9.4 审查禁区

- 禁止脱离本文件另造审查标准
- 禁止要求补模块级 docstring
- 禁止把 `"""摘要"""` 误判为合格 docstring
- 禁止把"缺少教程式解释"误判为 docstring 不完整
- 禁止把个人偏好包装成硬性缺陷
